## 二、第一阶段主要目标

第一阶段的主要目标不是立即得到性能最优的剪枝方案，而是验证以下流程能否完整运行：

```text
Benchmark Guide 数据
        ↓
剪枝重要性计算或结构选择
        ↓
模型剪枝
        ↓
剪枝模型保存与重新加载
        ↓
必要时进行 LoRA 恢复
        ↓
Benchmark Eval 数据评测
        ↓
形成可追踪的运行、结果和失败证据
```

结构化剪枝部分目前已完成上述流程的验证，并实现了实验性的 benchmark-guided Flab-Pruner 路径。

## 三、遇到的问题汇总

### 1. 官方仓库对目标代码模型支持不足

第一阶段原计划优先使用 Qwen2.5-Coder-1.5B 或 3B，以适应 RTX 5060 8 GB 等实验设备。但结构化剪枝方法的官方支持差异较大：

- Flab-Pruner 具有 Qwen 路径，但需要根据本项目环境进行适配；
- LLM-Pruner 的官方实现主要面向 LLaMA 类模型，对 Qwen 支持不足；
- SliceGPT 支持的模型和运行方式较为特殊；
- LaCo 主要提供面向 LLaMA/Baichuan 的 Notebook，缺少稳定、统一的执行脚本。

因此，实际复现中同时采用了：

- Qwen 本地适配；
- CodeLlama fallback；
- tiny 模型接口验证；
- 对官方支持不足的方法进行范围性排除。

### 2. 8 GB 显存限制影响 7B 模型复现

CodeLlama-7B 的 fp16 权重无法完全装入 8 GB 显存。尝试过：

- 4-bit 量化加载；
- GPU + CPU Offload；
- 减小 batch size；
- 降低最大序列长度。

这些措施能够缓解显存压力，但会带来明显问题：

- 量化会引入剪枝之外的新变量；
- CPU Offload 使生成速度大幅下降；
- 部分官方剪枝实现要求模型完整加载至 GPU，无法严格复现；
- 7B 路径很难在当前设备上进行大规模重复实验。

因此，后续逐步将 Qwen2.5-Coder-1.5B 作为剪枝的统一模型。

### 3. 剪枝流程能够运行，但生成能力出现断崖式下降

LLM-Pruner、SliceGPT 和 Flab-Pruner 的主要路径均完成了真实剪枝与评测，但剪枝模型的代码生成能力明显下降。

问题不仅表现为 pass@1 较低，还包括：

- 输出为空；
- 输出重复；
- 只生成特殊符号；
- 语法结构破坏；
- LoRA 恢复后仍未恢复到可接受水平。


### 4. “使用了 Benchmark Guide”不等于“由 Benchmark Guide 决定剪枝结构”

前期 Flab-Pruner 路径虽然读取了 guide 数据，但 guide 数据并没有真正决定模型保留哪些结构，因此不能称为严格意义上的 benchmark-guided 剪枝。

后续新增了实验性扩展，使 benchmark guide 的模型 activation 用于选择 FFN intermediate 通道，补齐了：

```text
Guide
→ activation importance
→ retained indexes
→ actual structural pruning
```


### 5. 正式评测与质量门需要区分

Flab benchmark-guided 的三个变体虽然都生成了真实剪枝模型，但在固定 20-task 质量门上出现严重重复字符输出。

因此按预先规则停止了完整正式评测。

这表述为：

```text
技术实现完成
+ 质量门失败
+ 正式全量评测按协议停止
```


或：

```text
正式 benchmark 得分为 0
```

## 五、结构化剪枝部分结果详述

### 5.1 Flab-Pruner 官方结构化路径

Flab-Pruner 的官方结构化路径已经完成真实剪枝：

- 使用 Qwen2.5-Coder 模型；
- 参数量真实下降至约 80%；
- 剪枝模型能够保存和重新加载；
- 完成 HumanEval、MBPP 和 LiveCodeBench eval half 评测；
- 尝试了 LoRA 恢复和 merge。

但模型能力下降明显：

- HumanEval：0/82；
- MBPP：1/224；
- LiveCodeBench：0/200。

说明当前结构化剪枝虽然在工程上可执行，但模型能力没有得到有效保留。

### 5.2 Flab-Pruner benchmark-guided 扩展

为了验证“benchmark 介入剪枝过程”，进一步实现了实验性的 benchmark-guided Flab 路径。

该路径完成了：

1. 使用 benchmark guide 样本执行真实模型前向；
2. 收集各层 FFN activation；
3. 计算 intermediate 通道重要性；
4. 根据重要性选择保留的 `intermediate_indexes`；
5. 调用 Flab 内部 `model.prune(zs)` 执行真实结构剪枝；
6. 保存和重新加载剪枝模型；
7. 比较不同 guide 产生的索引。

Qwen2.5-Coder-1.5B 的参数变化为：

```text
剪枝前：1,777,088,000
剪枝后：1,421,626,880
实际保留率：约 79.9976%
```

HumanEval、MBPP 和 LiveCodeBench guide 生成了不同的 importance hash 和 selected-index hash，证明 guide 数据确实改变了模型最终保留的 FFN 通道。

但三个变体在固定 20-task 质量门中均出现：

- `empty_rate = 0`；
- `duplicate_rate = 0.95`；
- 中位生成长度约 16 token；
- 不同题目几乎全部生成相同的连续感叹号。

因此三个变体均未通过非坍塌质量门，后续完整正式 benchmark 评测按协议停止。

这一结果说明：

> benchmark-guided 的技术链路已经打通，但目前采用的 activation importance 和 FFN-only 通道选择仍无法有效保留模型的代码生成能力。

此外，这一功能属于项目的实验性扩展，不是 Flab-Pruner 官方上游提供的 benchmark-guided 模式。

### 5.3 LLM-Pruner

LLM-Pruner 初期主要使用 CodeLlama-7B 尝试复现，但受到显存和官方加载方式限制，只能采用量化、CPU Offload 或较粗粒度 fallback。

后续建立了 Qwen2.5-Coder-1.5B 本地适配路径，并完成：

- 约 80% 参数保留；
- 模型保存和加载；
- 三项 eval half 正式评测；
- 历史 LoRA recovery 证据；
- primary 与 fallback 状态区分。

Qwen 主路径结果为：

- HumanEval：2/82，约 2.44%；
- MBPP：1/224，约 0.45%；
- LiveCodeBench：0/200。

CodeLlama layer-drop 路径保留为 `fallback_non_official`，不能作为完整官方 MetaPruner 复现。

当前结论是：

```text
执行闭环完成，但模型生成能力保留效果较差。
```

### 5.4 SliceGPT

SliceGPT 的早期 CodeLlama 路径受到 7B 模型和 CPU Offload 速度限制，只完成部分评测：

- HumanEval：82 题；
- MBPP：82 题；
- LiveCodeBench：未完成。

后续 Qwen2.5-Coder-1.5B 主路径完成三项正式评测：

- HumanEval：0/82；
- MBPP：2/224，约 0.89%；
- LiveCodeBench：0/200。

因此最终状态应区分：

```text
Qwen primary route：completed
CodeLlama legacy route：partial
quality gate：fail
```

### 5.5 LaCo

LaCo 官方只提供少量 Notebook，主要围绕 LLaMA/Baichuan 路径，缺少：

- 稳定 CLI；
- 明确的 CodeLlama/Qwen 支持；
- 完整的统一评测流程；
- 容易复现的模型保存与部署接口。

如果继续适配，需要较大程度重新实现算法，容易偏离“第一阶段真实复现”的目标。

因此项目决定：

```text
第一阶段不继续对 LaCo 进行大规模人工适配。
```

仓库中的 tiny layer-collapse smoke 仅作为探索性诊断，不代表官方 LaCo 复现完成。

- hidden、attention head 和 KV head 暂不由 benchmark guide 控制。

## 七、阶段性结论

### 1. 结构化剪枝部分已经完成

四种负责方法均有明确结论：

| 方法 | 结论 |
|---|---|
| Flab-Pruner | 官方结构化路径完成；benchmark-guided 扩展实现完成但质量门失败 |
| LLM-Pruner | Qwen 主路径完成，质量门失败 |
| SliceGPT | Qwen 主路径完成，质量门失败 |
| LaCo | 根据官方支持范围作出阶段性跳过决定 |

这里的“完成执行闭环”表示：

- 方法已真实执行或完成范围审计；
- 有可追踪的运行和失败证据；
- 有明确的质量结论；
- 不再处于 `planned` 或状态不明。

它不表示所有方法取得了良好性能。

### 1b. 非结构化剪枝部分也已形成明确结论

| 方法 | 结论 |
|---|---|
| Magnitude | Qwen 适配完成；全量 HE/MBPP 可报；OPT PPL 完成 |
| Wanda | Qwen 适配完成；全量 HE/MBPP 可报；OPT PPL 完成；10% 时 MBPP 最好 |
| DSnoT | OPT 与 Wanda 同协议 PPL 完成；Qwen 官方不支持，本阶段不报代码分 |
| OWL | 小模型流程完成；Qwen 官方不支持，本阶段不报代码分 |

和结构化组对比：同样在 Qwen-1.5B 上，非结构化 10% 稀疏后未出现输出坍塌；半集上 Dense / Mag / Wanda 的 HE、MBPP 仍有可用通过率（约 12–13/82、147–153/224），LCB 约 13–16/200，远高于结构化主路径接近 0 的结果。

### 2. 结构化剪枝当前最大的困难是能力保留

虽然目标参数保留率约为 80%，但三个主要方法的代码生成性能均出现明显下降。

这提示：

- 结构化剪枝的粒度可能过粗；
- 重要性估计可能与代码生成能力不匹配；
- 剪枝后的结构配置可能破坏预训练权重之间的协调关系；
- 一轮 LoRA 恢复不足以修复结构性损伤；
- 单纯以参数量保留率衡量剪枝强度并不充分。

### 3. Benchmark-guided 不能只停留在数据参与

第一阶段进一步确认：

> 只有 benchmark guide 真正改变最终保留结构，才能称为 benchmark-guided 剪枝。

Flab 扩展已经达到这一技术要求，但当前信号设计仍没有带来能力保留收益。

### 4. 目前结果价值

本阶段的结果说明：

- 代码大模型结构化剪枝并非直接套用官方脚本即可取得有效结果；
- 方法支持、模型架构、显存环境和评测设置都会显著影响结论；
- “能够剪枝”和“剪枝后仍能生成代码”是两个难度差距较大的要求；
- 质量门可以避免在模型已坍塌时继续消耗大量资源完成全量评测。

## 八、下一阶段规划

按照整体计划，第二阶段应重点在于引入 Agent，将多个剪枝方案应用至大模型上，再使用 SE-Agent 完成 eval 任务的方式来进行方法的优劣性测评。

根据第一阶段中遇到的问题，第二阶段应解决的遗留问题包括：

- 8G 显存只能运行 3B 及以下模型，需要使用性能较强的设备进行第二阶段的主要实验。可选选项包括租赁服务器或自配 PC。
- 需要解决剪枝后模型能力崩塌问题，该问题的来源可能有多种：第一阶段使用模型过小、冗余不足；第一阶段设置 max_new_token = 512 过小；LoRA 恢复层级不够等。
- 非结构化组：把 Dense / Mag / Wanda 的半集 HE、MBPP、LCB 对齐跑完，方便和结构化组同表对比；DSnoT / OWL 若要进 Qwen，需要单独做 adapter，否则继续只报 OPT / 小模型证据。
- 第二阶段引入 Agent / SE-Agent 测评时，优先用已经能力未坍塌的非结构化剪枝模型做对照组。
