## 分工

分工围绕剪枝方法的分类展开，具体为：

非结构化剪枝（潘阔）：Magnitude、Wanda、DSnoT、OWL；

结构化剪枝（常珂舒）：LLM-Pruner、Flab-Pruner、SliceGPT、LaCo（已排除）；

半结构化、自适应等（李长骏）：SparseGPT、MaskLLM、Pruner-Zero、FLAP；

## 遇到的问题汇总

1. 在执行书中考虑到三人电脑配置相对较低，决定统一使用 Qwen-1.5B 或 Qwen-3B 模型进行剪枝方案的复现，但是各剪枝方案官方仓库少有支持 Qwen 架构模型，如果需要在 Qwen 上做出复现需要自己写 Adapter。

    这里有两种选择：一是写出 Adapter 在 Qwen 上跑出方案复现（潘阔方案），其优点是符合电脑配置，可以在可接受时间内跑出结果，缺点是需要使用 AI Agent 来进行 Adapter 编写；

    一是选用 CodeLlama-7B 模型用于复现实验（常珂舒方案），优点是几乎所有方案都提供 Llama 家族模型支持，缺点是 7B 未量化版本无法在 8GB 显存中完全加载。

    在使用 CodeLlama-7B 尝试跑出复现的过程中，出现了 RTX 5060 显卡显存 8GB 无法完全加载 CodeLlama-7B 模型的问题，相应地采取了 4-bit 量化加载和 GPU + CPU Offload 两种解决措施，缺点也较为显著：4-bit 量化加载不符合只研究剪枝的变量设计，而 GPU + CPU Offload 会使单题生成时间从约 6s 延长至约 250s。

2. 第一阶段的关注点应在实验流程的跑通，从 Benchmark Guide 半集生成剪枝数据和 LoRA 恢复数据，进行剪枝后进行 LoRA 恢复，最后在 Benchmark Eval 半集进行评测。

    当前进度也与其相符，实验流程已跑通，但实验得到数据还需进一步加工。

    在横向对比实验数据时，发现 Eval 半集评测的数据有很大差异，例如在非结构化剪枝路线上，Qwen 模型未剪枝前的通过率大概在 15% HumanEval 和 60% MBPP，剪枝后通过率在可接受范围内降低；但在结构化剪枝路线上，在 Qwen 模型未剪枝前数据相近的前提下，剪枝后通过率为 0% HumanEval 和 2% MBPP。还需要进一步检查实验变量设置。

3. 官方仓库脚本提供不完全问题：如 LaCo 方案官方只给出两个 Notebook 而并未给出可运行脚本，Notebook 主要面向 LLaMA/Baichuan 路线，官方支持过少，并不明确支持 CodeLlama，因此当前阶段将 LaCo 排除。

## 结果详述

### 非结构化剪枝组

1. Magnitude：官方不单独成仓，挂在 Wanda 仓库里跑。OPT-125M 上 30% 稀疏 PPL 约 34.5，50% 直接崩到约 193。Qwen-1.5B 自己接了适配后，10% 稀疏时 HumanEval / MBPP 还能撑住，30% 掉得更明显。

2. Wanda：同样在 Qwen-1.5B 上写了适配才跑通。OPT 上明显好于 Magnitude（30% PPL 约 28，50% 约 39）。Qwen 上 10% 稀疏时 MBPP 最好，大约 68%；HumanEval 未剪枝大约 15%，剪枝后也差不多这个水平，没有断崖。

3. DSnoT：在 OPT 上接在 Wanda 后面做修正，30% 时和 Wanda 差不多，50% 时略差一点，增益不大。官方不支持 Qwen，这阶段没在 Qwen 上出代码通过率。

4. OWL：小 Llama 上流程跑通了，能做出非均匀层稀疏；同样不支持 Qwen，这阶段也没有 Qwen 代码通过率。

#### 实验设置：

* 代码侧模型用 Qwen2.5-Coder-1.5B-Instruct，语言建模对照用 OPT-125M；
* OPT 稀疏率 30% / 50%，校准样本 128；Qwen 稀疏率 10% / 30%，校准用 32 条 guide；
* MaxNewTokens 设为 512；
* 解码方式为贪心解码，do_sample=False；
* batch size 1；
* 代码评测用全量 HumanEval 和 MBPP（evalplus），不是半集。

### 结构化剪枝组

1. LaCo：如上，LaCo 官方给出的源码过少，只给出针对 Llama/BaiChuan 的剪枝 Notebook 而无官方脚本。

2. Flab-Pruner：只支持 Qwen 架构，不支持 Llama 家族，但进行剪枝后观察到模型能力断崖式下滑，还需进一步排查实验设置等问题；

3. LLM-Pruner：不支持 Qwen 架构，本次实验使用 CodeLlama-7B 模型进行运行，由于模型本身 fp16 无法在 8GB 显存上完全加载，使用 4bit 加载 Guide 半集获得剪枝和 LoRA 数据，对 fp16 模型本身剪枝，再使用 4bit 加载 Eval 半集获得测试数据的方式。

    另外由于官方方案剪枝加载强制要求完全加载至 GPU 上，无法对官方方法进行完整复现。采用了粒度更粗但原理相同的方案，计算 Guide 阶段梯度重要性，后续进行层粒度的剪枝。

    可能由于 4bit 加载过粗，或者实验设置问题，在 CodeLlama-7B 未剪枝的评测数据上便出现了 0% HumanEval 和 0% LiveCodeBench 的问题。也需要再进行排查。

4. SliceGPT：本身无法进行剪枝而生成一个新的模型，而是需要“附着”在 fp16 模型上进行运行，因此无法进行量化加载，必须使用 GPU + CPU Offload 的方法加载并且跑实验，单题运行时间约 250s，运行 10 小时后仅跑出 HumanEval 82题 + MBPP 82题，并且通过率仍为 0。这说明实验设置本身可能存在相当大的问题。

#### 实验设置：

* 剪枝方案统一保持约 Keep 80%，由于 Flab-Pruner 等粒度为层，不精准保证 Keep 80%；
* MaxNewTokens 设为 256；
* 解码方式为贪心解码，do_sample=False；
* batch size 1；
* LoRA rank=8，alpha=16，dropout=0.05（Flab-Pruner）/0（LLM-Pruner）；
* LoRA epoch=1；
* LoRA max length=512（Flab-Pruner）/256（LLM-Pruner）；
* 半集划分原则为：HumanEval 与 LiveCodeBench 采用分层后交错/奇偶划分，使不同难度、不同题型任务尽量均匀分布到 guide half 和 eval half。MBPP 基于官方划分： prompt / train / validation split -> guide half；test split -> eval half。
